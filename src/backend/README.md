# Backend

Phase 3 is implemented: Supabase SSR client/schema types, authoritative session guards, runtime configuration, HTTP input/error helpers, and profile service. Next.js HTTP handlers in `src/app/api` delegate to this layer. Authentication callbacks are in `src/app/auth`; session refresh runs in `src/proxy.ts`.

Server modules import `server-only`. Never import these into frontend modules. The app uses only the public Supabase key plus the user's verified cookie session; no service-role key is used. Owner-only writes run through `save_my_profile`, whose migration enforces its actor/verification checks independently of the HTTP handler. Phase 4 adds the catalogue/selections/discovery service. `replace_my_skills` derives the verified owner and serializes whole-set writes; `discover_members` computes paginated explanations without exposing private account data. Phase 5 adds restricted booking routines and a server-only booking service: participant reads, funded requests, transitions, expiry, idempotency and overlap prevention. Phase 6 adds wallet reads, one-time issuance, reservations, releases, balanced ledger transfers, two-party completion and mutual dispute votes. Phase 7 adds bounded participant-only in-app grants to an explicitly public Jitsi classroom demo. Public room access outside the app is not controlled by these guards.
